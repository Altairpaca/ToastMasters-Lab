## 1. 项目概述

### 1.1 背景

头马（Toastmasters）俱乐部日常运营依赖大量重复性事务：会前议程表制作、来宾报名接龙、备稿申请、评选投票；会中三官（计时官 Timer / 哼哈官 Ah-Counter / 语法官 Grammarian）记录；会后纪要、复盘、成长数据沉淀。

现状存在三个典型痛点：

1. **工具割裂，数据不通**：上游参考站 `gctoastmaster.club` 的约 40 个单文件 HTML 工具彼此独立，同一期会议的信息（人、角色、时间、记录）在多个工具间重复录入，无法串联。
2. **数据深度绑定平台**：成长类数据（报告、出勤、进步曲线）需权限或依赖第三方服务，俱乐部无法自主掌控。
3. **议程表保真难**：既有俱乐部议程 xlsx 含 EMF/Logo/二维码等富对象，通用工具（如 openpyxl）会破坏格式；开源生态中的议程工具无一能保真输出既有俱乐部格式。

Altair 已在本地完成部分复刻：`头马三官助手/离线版/` 下已有改造过的 `universal-timer.html`、`gc-ah-counter.html`、`gc-grammarian.html`，具备三视图报告、零依赖 GFM 渲染、Canvas 自绘 PNG 等自研能力；`议程表/` 下沉淀了完整的制表规则与「XML 直改 sheet1.xml + sharedStrings.xml」的保真制表方法。

### 1.2 问题定义

**一句话**：俱乐部缺少一套**可插拔、可自持、可离线、覆盖会前→会中→会后全流程**的工具链，且每个工具应以独立形态（自包含 HTML / 小程序 / BS 模型）交付、独立成 repo。

### 1.3 产品目标（Goals）

1. **全流程贯通**：以单一数据源 `meeting.json` 打通「会前议程/接龙 → 会中三官记录 → 会后纪要/复盘」，同一期会议数据只录一次。
2. **可插拔模块化**：每个功能模块边界清晰、契约明确，可独立使用、可替换实现（同一渲染内核在 HTML 版与小程序版间复用）。
3. **多形态可选交付**：同一功能可提供「类 GC 自包含单文件 HTML」「小程序 + 轻量服务端」「BS 模型」等不同版本，各版本独立成 repo。

### 1.4 非目标（Non-Goals）

明确**不做**以下内容，以控制范围：

- ❌ 多分会连锁管理 / 总部级多租户后台（本项目面向单俱乐部自持使用）。
- ❌ 会员付费、证书、Pathways 官方进度对接（无官方公开自助 API）。
- ❌ 云原生大规模部署 / 高并发 SaaS（零后端优先，小程序服务端仅作最小必要）。
- ❌ 与 Toastmasters International 官方系统双向同步。
- ❌ 复杂权限体系 / SSO（单俱乐部场景，最简鉴权即可）。

## 2. 产品定位与差异化

| 维度 | TMC Toolkit 定位 |
|------|------------------|
| **全流程** | 市面上**唯一**覆盖「会前议程 → 会中三官 → 会后复盘」的完整链路；开源生态中议程类、计时类、三官类各自为战，无端到端方案 |
| **保真导出** | **唯一**支持保真输出既有俱乐部 xlsx 格式（保留 EMF/Logo/二维码），采用「复制最近一期作底稿 + XML 直改」手法 |
| **真离线** | 类 GC 版为单文件零依赖 HTML，`file://` 直开、断网可用、无需安装、无需账号 |
| **零后端** | 默认本地优先，数据存本机（localStorage / 文件下载），俱乐部自主掌控，不被平台绑架 |
| **可插拔** | 模块契约化，议程模块、三官模块、接龙模块可单独取用，也可组合成完整套件 |

**核心差异化一句话**：*别人给工具，我们给可自持、可离线、可保真、能串起来的工具链。*

## 3. 形态与交付矩阵（核心）

用户明确要求「不同版本作为不同 repo 开发」。规划以下四类形态：

### 形态 A：类 GC 自包含单文件 HTML 版

| 项目 | 说明 |
|------|------|
| **适用场景** | 离线现场使用（会场无网/弱网）、个人电脑直接双击打开、U 盘拷给他人、微信文件传输后本地打开 |
| **技术选型约束** | 单文件 HTML，零外部 js/css/CDN，`file://` 直接可用；数据通过 localStorage + 文件导出（.json/.png）持久化；延续已有 `mdToHtml()`、`buildReportImage()`、`colorizeStatus()` 等自研内核 |
| **典型模块** | 通用计时官、哼哈官、语法官、议程预览、报告渲染 |
| **Repo 归属** | `tmc-officers-html`（三官）、`tmc-agenda-html`（议程，如采用纯 HTML 实现） |
| **优点** | 极致轻量、真离线、零运维；**缺点** | 无跨设备同步、协作弱、小程序端无法直接用 |

### 形态 B：小程序友好 / BS（浏览器-服务器）模型版

| 项目 | 说明 |
|------|------|
| **适用场景** | 会前多人协作（报名、备稿、投票）、需要跨设备共享同一期会议数据、微信生态内传播 |
| **技术选型约束** | 前端：微信小程序（原生或 Taro）；服务端：极轻量（可用云函数 / Serverless，或自建最小 HTTP 服务）；数据：服务端 JSON 存储 + 小程序本地缓存兜底；**因平台限制可例外**，允许引入后端与网络依赖 |
| **典型模块** | 报名接龙、备稿申请、评选投票、来宾通道、议程在线协作 |
| **Repo 归属** | `tmc-miniprogram`（小程序端）、`tmc-server-lite`（可选的最小服务端） |
| **优点** | 协作强、传播易、跨设备；**缺点** | 有运维成本、需服务端、隐私需说明 |

### 形态 C：会前议程表制作 / 接龙模块

| 项目 | 说明 |
|------|------|
| **适用场景** | 事务官/教育副会长会前制作议程、发起报名接龙、收备稿申请 |
| **技术选型约束** | **双形态**：① 自包含 HTML 版（本地制作 + 导出保真 xlsx）；② 小程序版（在线接龙/报名，用户明确提出「可小程序化」）。xlsx 导出必须保真（XML 直改法） |
| **典型模块** | 议程生成器、xlsx 保真导出、接龙（rsvp）、备稿申请、投票 |
| **Repo 归属** | `tmc-agenda-html` + `tmc-miniprogram`（接龙/报名部分） |
| **优点** | 覆盖会前高频痛点、直击保真导出；**缺点** | xlsx 保真依赖模板维护 |

### 形态 D：会中三官记录模块

| 项目 | 说明 |
|------|------|
| **适用场景** | 会中三官现场记录与即时出报告（用户明确提出「单客户端自包含 HTML」方式） |
| **技术选型约束** | 单客户端自包含 HTML，零依赖、`file://` 直开；报告支持多视图 + Canvas 自绘 PNG 导出；ASR/联网功能须**优雅降级**（离线时不可用但不报错） |
| **典型模块** | 计时官（universal-timer）、哼哈官（ah-counter）、语法官（grammarian）、报告渲染内核 |
| **Repo 归属** | `tmc-officers-html` |
| **优点** | 现场零依赖、可靠；**缺点** | 单机数据、会后需导出汇总 |

### 形态矩阵总览

| 形态 | 交付物 | 后端 | 离线 | 协作 | 主要 Repo |
|------|--------|------|------|------|-----------|
| A 自包含 HTML | 单文件 .html | 无 | ✅ 真离线 | 弱 | `tmc-officers-html` / `tmc-agenda-html` |
| B 小程序/BS | 小程序 + 服务端 | 轻量 | 部分（缓存兜底） | 强 | `tmc-miniprogram`（+ `tmc-server-lite`） |
| C 议程/接龙 | HTML + 小程序 | 视版本 | HTML 版✅ | 小程序版强 | `tmc-agenda-html` + `tmc-miniprogram` |
| D 三官记录 | 单文件 .html | 无 | ✅ 真离线 | 弱 | `tmc-officers-html` |

## 4. 可插拔模块化设计需求

### 4.1 模块边界与契约

| 模块 | 输入 | 输出 | 依赖 | 可替换实现 |
|------|------|------|------|-----------|
| **议程生成器** | 会议元数据 + 角色分配 + 模板 | 议程预览 + 保真 xlsx | 模板 xlsx、`meeting.json` | HTML 版 / 小程序版 |
| **xlsx 保真导出** | 底稿 xlsx + 议程数据 | 保真 xlsx（保留 EMF/Logo/二维码） | 无外部库（XML 直改） | 唯一实现（保真方法固定） |
| **接龙/报名** | 会议 ID + 来宾信息 | 报名清单 | 存储层 | HTML 本地 / 小程序在线 |
| **备稿申请** | 会议 ID + 会员 + 项目要求 | 备稿队列 | `meeting.json` | 同上 |
| **评选投票** | 候选列表 | 投票结果 | 存储层 | 同上 |
| **三官记录** | 会议 ID + 现场事件 | 三官记录数据 | 存储层 | 计时/哼哈/语法分模块 |
| **报告渲染内核** | 记录数据 | 多视图 HTML + PNG | 无 | **HTML 版与小程序版应共用同一渲染逻辑** |
| **存储层** | 键值读写 | 持久化 | 无 | localStorage / 文件 / 服务端 API |

### 4.2 关键设计原则

1. **渲染内核复用**：`报告渲染内核`（mdToHtml / buildReportImage / colorizeStatus）应与宿主解耦，纯函数化，HTML 版与小程序版通过适配层复用。
2. **数据契约先行**：所有模块以 `meeting.json`（见 §7）为单一事实源，模块间不直接耦合。
3. **存储层可替换**：业务逻辑不直接调用 localStorage，通过存储适配器接口，便于切换到服务端。
4. **降级友好**：联网增强功能（如 ASR）必须可被关闭，关闭后核心功能不受影响。
5. **零依赖优先**：HTML 版禁止引入外部 CDN/包；小程序版依赖最小化。

## 5. 用户故事与用户旅程

### 5.1 用户旅程

**T-3 天（会前筹备）**
事务官/教育副会长：新建本期会议 → 选择底稿模板 → 填角色分配 → 导出保真 xlsx → 发起报名接龙/备稿申请 → 收集来宾与备稿信息。

**T-0（会中现场）**
三官：打开自包含 HTML 工具（无需网络）→ 计时官记录各环节用时、哼哈官记录赘词、语法官记录妙语/每日一词 → 现场即时生成报告并导出 PNG/HTML。

**T+1（会后复盘）**
教育副会长/事务官：汇总三官记录与报名数据 → 生成会议纪要与复盘报告 → 归档到 `meeting.json` 相关记录 → 沉淀成长数据。

### 5.2 用户故事（按角色）

- **As a 事务官**, I want 一键生成保真的议程 xlsx（保留 Logo/二维码）, so that 无需手工重排格式。
- **As a 事务官**, I want 发起在线报名接龙, so that 来宾与会员可自助报名。
- **As a 教育副会长**, I want 统一收集备稿申请与项目要求, so that 排期不冲突、项目进度可追踪。
- **As a 三官（计时/哼哈/语法）**, I want 断网也能用的单文件工具, so that 现场记录不被网络影响。
- **As a 三官**, I want 现场即时出多视图报告并导出图片, so that 可在会议群直接分享。
- **As a 教育副会长**, I want 会后把全部数据汇入单一会议档案, so that 复盘与成长分析有据可依。

3. **是否做小程序服务端**：形态 B 是否引入最小服务端（`tmc-server-lite`），还是先只做纯前端 + 小程序云开发？
4. **是否引入 CI**：是否需要 GitHub Actions 跑 `_selftest.js` 单测？
5. **Repo 粒度**：是否把「报告渲染内核」独立成 `tmc-render-core`，还是内嵌在主 repo 内（初期可内嵌，稳定后再抽）？
6. **xlsx 底稿模板**：保真制表依赖「最近一期作底稿」，是否需要一个中立的空白模板库？
7. **小程序主体**：是否有已认证的小程序 AppID，还是先用体验版/个人号？
8. **数据隐私**：来宾联系方式等敏感信息在云端存储时的保留与删除策略？
9. **命名确认**：`tmc-toolkit` 等仓库名是否符合偏好（备选 `toastmasters-toolkit`）？
